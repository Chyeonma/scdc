# P7-T01: upload attachment

Local Compose chạy SeaweedFS S3-compatible tại `http://localhost:8333` với bucket riêng `scdc-messaging`, và ClamAV ở `127.0.0.1:3310`. API dùng MinIO .NET SDK làm S3 client. Hai service chỉ phục vụ mạng nội bộ của ứng dụng; không cấp quyền đọc bucket công khai. Cấu hình production qua biến môi trường `Modules__Messaging__Attachments__Endpoint`, `AccessKey`, `SecretKey`, `Bucket`, `ClamAvHost`, `ClamAvPort`; không đặt secret production vào source. Database đã có phải chạy `database/postgres/migrations/20260925_p7_t01_attachment_uploads.sql` trước khi khởi động API mới.

Luồng upload qua API:

1. `POST /api/v1/spaces/{spaceId}/attachments` dùng `multipart/form-data` với `file`, `clientUploadId` (UUID do client tạo) và `checksumSha256` (64 ký tự hex SHA-256 của bytes file). Chỉ thành viên còn quyền gửi mới được upload; DM có block không cho upload. Mỗi file từ 1 byte đến 10 MiB, tên tối đa 255 ký tự. Server đọc toàn bộ bytes có giới hạn, so checksum, đối chiếu phần mở rộng với chữ ký PNG/JPEG/GIF/WEBP/PDF hoặc UTF-8 text rồi quét ClamAV. MIME do client gửi không quyết định loại file. ClamAV lỗi thì upload thất bại đóng; file bị phát hiện không được lưu vào object storage.
2. Một dòng `messaging.attachment_uploads` được tạo ở trạng thái chờ quét, với owner, space, `clientUploadId`, checksum, object key không đoán được và hạn dùng 24 giờ. Chỉ file sạch (`scan_status = 1`) được ghi vào bucket; phản hồi trả ID upload. Retry cùng `clientUploadId` và cùng bytes/tên trả lại ID cũ, không tạo object mới; payload khác bị từ chối. Trạng thái 2 là bị chặn, 3 là lỗi quét/lưu trữ. Không có URL download ở task này.
3. `POST /api/v1/spaces/{spaceId}/messages` nhận `attachmentIds` tối đa 5 ID, cùng `clientMessageId` và `messageType`. Dùng `messageType = 3`, `content = null` cho attachment-only; dùng `messageType = 1` với nội dung chữ để gửi text kèm file. Server chỉ chấp nhận upload sạch, chưa hết hạn, chưa gắn message, đúng owner và space. Message, metadata `messaging.attachments`, trạng thái upload và outbox cùng transaction. Retry với cùng `clientMessageId` và payload trả lại message cũ; dùng lại file cho message mới bị từ chối.
4. Worker hàng giờ xóa object và staging row của upload chưa gắn message đã quá hạn. Nếu xóa object lỗi, row được giữ để retry lần sau. Khi message bị xóa vật lý, FK đặt upload về chưa gắn và worker dọn sau khi hết hạn. Xóa mềm message giữ metadata để chính sách tải/xóa file của P7-T02 có thể xử lý tiếp.

Giới hạn upload là 10 MiB/file, 5 file/message, tối đa 20 upload sạch/chờ chưa gắn tin mỗi tài khoản và dùng chung giới hạn 30 thao tác gửi/upload mỗi phút. API trả metadata đã xác thực.

## P7-T02: xem và tải xuống

`GET /api/v1/spaces/{spaceId}/attachments/{attachmentId}/download` yêu cầu bearer token và trả file qua API, với `Content-Disposition: attachment`, MIME đã được server xác minh, `Cache-Control: no-store` và `X-Content-Type-Options: nosniff`. API kiểm tra user còn hoạt động, còn quyền đọc space, attachment nằm trong message của space đó, message/file chưa bị xóa và file đã qua quét (`scan_status = 1`). ID không tồn tại và trường hợp không có quyền cùng trả 404. Bucket không public và không cấp URL ký; sau khi thu hồi quyền, mọi request download **mới** bị chặn, còn request đã qua bước kiểm tra quyền có thể hoàn tất. Client dùng blob URL tạm cho preview ảnh/tải xuống rồi thu hồi blob URL khi không còn dùng.

Composer giữ đối tượng `File` gốc tới khi upload thành công; hiện tiến độ, cho hủy/thử lại với cùng `clientUploadId`, và hiển thị riêng trạng thái "Đã tải lên, chưa gửi" trước khi message được tạo. Sau khi gửi, timeline và thread hiển thị tên, kích thước, thumbnail ảnh và nút tải xuống. Tên file là text React, không được đưa vào HTML thô. Nếu upload mất mạng hoặc quét/lưu trữ lỗi, draft và file còn để thử lại; send message dùng `clientMessageId` ổn định cùng danh sách upload ID để tránh nhân đôi khi retry. File quá lớn và phần mở rộng không hỗ trợ được báo sớm ở client, nhưng server vẫn kiểm tra bytes/checksum/định dạng và quyết định cuối cùng.
